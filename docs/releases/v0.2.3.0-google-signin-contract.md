# JagaKebond 0.2.3.0: Sign in with Google + admin registration inbox

> **Release** 0.2.3.0 · **Status** shipped

Owner decisions (2026-10-28):
- Anyone with a Google account may ask to join. The request lands in an admin inbox, and the admin approves or rejects it.
- Google sign-in appears on the website and in the Android app.

## Flow

Security continuation (2026-10-29): the owner explicitly allows Google sign-in for
admins. Their existing role, seven-day session cap, and password confirmation for
sensitive admin actions remain in force.

1. Client: `GET /api/auth/google/config` returns `{enabled, clientId}`, plus a nonce from `POST /api/auth/google/nonce`.
   - The nonce is random, single use and valid for 10 minutes; it is stored server-side.
   - `enabled` is false until `GOOGLE_CLIENT_ID` is set in `.env`. Until then no Google UI is shown anywhere.
2. Client obtains a Google **ID token** carrying that nonce:
   - **Web:** the Google Identity Services button (`accounts.google.com/gsi/client`), with the `nonce` set.
   - **Android:** a native Credential Manager call (`GetSignInWithGoogleOption`, serverClientId = the web client ID, nonce), exposed by `JagaSyncPlugin.googleSignIn`. Google blocks its web sign-in inside WebViews, so the app does not use the web button.
3. `POST /api/auth/google {credential, nonce}`. The server verifies the token:
   - RS256 signature against Google's JWKS (`https://www.googleapis.com/oauth2/v3/certs`, cached per Cache-Control, refetched once on an unknown `kid`);
   - `iss` is `accounts.google.com` or `https://accounts.google.com`;
   - `aud` is one of the configured client IDs;
   - `exp` is in the future (60 s skew allowed) and `iat` is not in the future;
   - `nonce` matches an unused server nonce, which is then consumed;
   - `email_verified` is true.
4. Outcome:
   - The Google `sub` is already linked to an account. If the account is active, a normal session is created (same cookies, CSRF and TTL as password login). If it is inactive: 403 "Akun dinonaktifkan".
   - No link, but an active account has the same email (case-insensitive): auto-link only if it was admin-created or has never established a password session. This applies to admins too. Self-registration counts as password use. Existing accounts with missing provenance are conservatively sent to the inbox. An account already linked to another Google identity cannot auto-link again. The lookup and insert share one transaction.
   - Otherwise a **registration request** is created or refreshed (`sub`, email, name), with status `pending`. Response: 202 `{code: "registration_pending"}`. The UI shows "Permintaan masuk sudah dikirim. Tunggu persetujuan admin."
   - If the request was `rejected`, the response is 403 `{code: "registration_rejected"}`.
5. **Admin inbox** (admin console, "Pendaftaran" card): lists pending requests with email, name and time.
   - **Setujui:** creates a `user` account with no password (password login stays impossible until the admin sets one) and links the `sub`. The next Google sign-in works.
   - **Tolak:** the request is marked rejected.
   - Both actions ask for the admin's password, like other sensitive actions, and both are audited.

## Limits

- Pending requests are capped at 200 in total.
- New requests are capped at 20 per normalized IP per 24-hour window; refreshing a pending request does not spend another slot. The budget persists across restarts.
- Pending requests expire 30 days after creation, even if refreshed. Approval and rejection decisions are retained.
- One request per Google `sub`; repeating refreshes `updated_ms`.
- Per-IP Google failure throttling uses a separate `google:<IP hash>` counter and does not affect password-login counters. Failed token and nonce checks are audited without token contents.
- Nonce table: at most 5000 live rows globally and 20 per normalized IP; expired rows are purged. IPv6 addresses in one /64 share a budget.
- JWKS fetches run outside the cache lock; concurrent callers share one fetch. Cold-cache failures are negatively cached for 10 seconds, with a 5-second HTTP timeout and 2-second connect timeout.

## Storage (schema 10)

```
google_identities(sub TEXT PRIMARY KEY, account_id TEXT NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
                  email TEXT, created_ms INTEGER, last_login_ms INTEGER)
registration_requests(id TEXT PRIMARY KEY, sub TEXT UNIQUE NOT NULL, email TEXT NOT NULL, name TEXT,
                      status TEXT NOT NULL CHECK(status IN ('pending','approved','rejected')),
                      created_ms INTEGER, updated_ms INTEGER, decided_ms INTEGER, decided_by TEXT, account_id TEXT)
auth_nonces(nonce TEXT PRIMARY KEY, ip_hash TEXT NOT NULL DEFAULT '', expires_ms INTEGER NOT NULL)
google_request_limits(ip_hash TEXT PRIMARY KEY, window_start_ms INTEGER NOT NULL, requests INTEGER NOT NULL)
```

Schema 10 also adds `accounts.admin_created` and `accounts.last_password_login_ms`.
The 9-to-10 migration backfills trusted creation provenance from existing admin roles
or contemporaneous creation audit records; uncertain legacy accounts require review.
These changes belong to the unreleased schema-10 migration. Never reuse an earlier
development schema-10 database; use fresh synthetic fixtures or a schema-9 upgrade.

If a pending request matches an existing password-used account, approval returns
`email_taken` rather than silently merging identities or preserving a planted
password/session. An admin must resolve account ownership before approving.

Accounts created on approval have `password_hash` set to an unusable marker that `verify_password` always rejects.

## Security headers

The field app CSP is widened only for Google's sign-in origins:
- `script-src https://accounts.google.com/gsi/client`;
- `frame-src https://accounts.google.com/gsi/`;
- `connect-src https://accounts.google.com/gsi/`;
- `style-src https://accounts.google.com/gsi/style`.

`/admin` stays strict. Google's popup needs `Cross-Origin-Opener-Policy: same-origin-allow-popups` (or no COOP).

## Owner setup (cannot be done by Claude: it needs the owner's Google account and accepting Google's terms)

1. Google Cloud console:
   - create a project;
   - set the OAuth consent screen to External, app name JagaKebond, support email, authorised domain `jagake.bond`;
   - publish it.
2. Credentials → OAuth client ID → **Web application**, with authorised JavaScript origin `https://jagake.bond`. Copy the client ID. It is public, not a secret.
3. Credentials → OAuth client ID → **Android**:
   - package `jagake.bond.app`;
   - SHA-1 of the app signing certificate (Claude provides it from the APK).
4. Send Claude the web client ID. Claude puts `GOOGLE_CLIENT_ID=` into the VPS `.env` and restarts the service.
